01 · Product thesis

Investigate relationships, not isolated alerts

Do not build another dashboard that lists isolated vulnerabilities. Build a security investigator that follows graph relationships to explain which combinations of permissions, tools, repositories and resources create a plausible attack path — and which validated change breaks that path.
Problem

Risk is connected

Individual alerts miss how tool permissions, repo access, dependencies, secrets exposure and workflow privileges combine into a larger risk.

Solution

Investigate relationships

FalkorDB stores and traverses the security model; an agent uses controlled graph-query tools and produces explainable attack-path findings.

Business outcome

Prioritize useful fixes

Show which verified policy or config change removes the most validated risk without breaking legitimate developer workflows.

MVP boundary

GitHub and CI/CD first

Repo metadata, workflow permissions, scan findings and a controlled AI-agent test harness. Live enforcement only for supported integrations.

Scope rule
A graph path is a candidate relationship, not proof of exploitability. Always distinguish observed events, static findings, simulated tests, external intelligence and AI-generated hypotheses.

Graph query concept

Core traversal · Cypher

MATCH (a:Agent)-[:CAN_INVOKE]->(t:Tool)
  -[:HAS_PERMISSION]->(p:Permission)
  -[:CAN_ACCESS]->(r:Resource)
WHERE a.id = $agent_id
  AND r.sensitivity IN ['confidential','restricted']
RETURN a.id AS agent, t.name AS tool,
  p.scope AS permission_scope,
  r.id AS resource, r.sensitivity AS sensitivity
LIMIT 100

-- add a tenant/project constraint in production
Graph design rules
  • Stable internal IDs with uniqueness constraints and indexes
  • tenant_id and project scope on nodes; enforced in the query service, not prompts
  • Explicit provenance: assertion_source, observed_at, validation_status
  • Upserts and stable external IDs so replayed webhooks never duplicate
  • Bound depth, result count, query time and relationship types
  • No secrets, credentials or large source files in graph properties

Data integrity rules
  • UUIDs internally; unique tenant-scoped external IDs and idempotency keys
  • Fingerprint dedupes findings but is not permanent identity
  • Timestamps in UTC; preserve source timestamps
  • Transactions for status changes, approvals and audit writes
  • Large artifacts in access-controlled object storage
  • Retention keeps legally required audit records
Anti-pattern
Don't duplicate the graph into tables and treat FalkorDB as a visualization layer. The graph is the security model; Postgres is the transactional index around it.

Request

    "agent_ids": ["agent-uuid"]

  "max_hops": 5,
  "max_paths": 20,
  "include_external_intelligence": false
}

Response

HTTP/1.1 202 Accepted
{
  "investigation_id": "investigation-uuid",
  "job_id": "job-uuid",
  "status": "queued",
  "status_url": "/api/v1/jobs/job-uuid"

Contract rules
  • 202 Accepted with job id, status and status URL for queued jobs
  • Idempotency keys for webhooks, remediations, PRs and verification
  • Cursor pagination with bounded page size and sort fields
  • Stable error codes — no secrets, stack traces or cross-tenant hints
  • Cancellation never assumes an executed external action rolled back

09 · Severity, risk score & confidence

Severity estimates impact; confidence measures support

Severity levels

CriticalVerified high-impact compromise or validated path to highly sensitive production assets
HighCredible path to unauthorized access, privilege abuse or sensitive-data disclosure
MediumMaterial impact but needs additional preconditions or has limited reach
LowLimited-impact weakness or defense-in-depth improvement
InformationalObservation or hardening advice without demonstrated impact
risk_score
risk_score = 100 × Σ (weight × factor) — each factor normalized 0–1 with documented criteria and calibrated on a labeled test set. A verified high-impact event can override policy; an unverified LLM assertion cannot.

Evidence confidence bands

ConfirmedDirect telemetry or deterministic, reproducible check
StrongRepeatable sandbox test shows the behavior
ModerateStatic analysis shows a risky condition; runtime untested
TentativeHeuristic or model hypothesis, uncorroborated

Graph path validation states

candidateGraph relationships suggest a possible path
needs_evidenceOne or more critical relationships need confirmation
validatedRequired edges and conditions checked against evidence or a reproducible test
disprovenEvidence contradicts the path
Connectivity ≠ exploitability
An agent with both file access and network access does not prove it can exfiltrate a sensitive file. Verify effective permissions, tool semantics, execution context and policy constraints.

10 · Evidence & provenance

What was observed, where, when — and what it proves

Evidence types
  • GitHub workflow / config excerpt
  • Scanner result with tool and rule version
  • Graph traversal output and edge provenance
  • Sandbox test input, output, exit status
  • CI run / commit / PR reference
  • External advisory or threat intel
  • LLM hypothesis, clearly labeled
Evidence metadata
  • Evidence ID and linked finding / observation
  • Source type, URL or artifact reference
  • Collection time and source timestamp
  • Content hash and collector version
  • Trust level and validation status
  • Exact claim supported, and limitations
  • Sanitization / redaction status
Display requirements
  • Sanitized preview by default; authorization for full artifact
  • Link every attack-path edge to its evidence
  • Separate source facts from AgentShield interpretation
  • Never let the model fabricate citations
  • Show contradictory or stale evidence
  • Search results are not proof of maliciousness

Optional external threat intelligence

Search corroborates evidence — it is never the engine.

SerpApi usage
Can gather public advisories and reports about a package, action, MCP server or domain. Show how a source changes or corroborates a specific investigation — and never call something malicious just because search results mention it.

11 · Remediation workflow

Every fix is proposed, approved, applied and proven

Proposal & verification — closure requires proof, not a merged PR

Remediation proposal (generic schema)

{
  "finding_id": "finding-uuid",
  "strategy": "least_privilege_workflow_permissions",
  "summary": "Restrict workflow token permissions
              to required scopes",
  "proposed_change": {
    "file": ".github/workflows/build.yml",
    "diff_ref": "controlled-artifact-reference"
  },
  "expected_effect": {
    "path_ids_to_recheck": ["path-uuid"],
    "risk_reduction_claim":
      "Remove unnecessary write capability"
  },
  "requires_approval": true
}
Verification conditions
  • The exact approved proposal version was applied or merged
  • Relevant scanner and CI tests pass
  • Target path removed or downgraded for an evidence-backed reason
  • Negative tests confirm the prohibited action is blocked
  • Positive tests confirm legitimate operations still work
  • Result links to commit, CI run, policy version and evidence

13 · Securing AgentShield itself

A security product must meet its own bar

Identity & tenancy

Tenant-scoped authz on every API, query, artifact and job. RBAC: admin, analyst, developer, auditor. Integration identity separate from users.

Secrets & artifacts

Secrets manager for App keys, webhooks and LLM credentials. Nothing in graph, prompts or logs. Short-lived authorized download URLs.

Graph & agent boundary

Allowlisted graph tools, parameterized and capped. Tenant filters inside the query service. Repo text and PRs treated as prompt-injection risk.

Execution & network

No untrusted code during ingestion. Tests in isolated ephemeral environments. Block private-network SSRF; validate URLs, archives, payloads.

Remediation integrity

Approval binds to proposal hash, repo, branch and scope. Separate propose / approve / execute / verify. Idempotent, audited external actions.

Reliability & privacy

Encrypt in transit and at rest. Retention and deletion rules. Bound tokens, iterations and runtime. No private code to external models without consent.

Threat model — seven threats, each with a control and a test

ThreatControl & test
Prompt injection in repo contentUntrusted content is data, never policy; test override and secret-request attempts
Cross-tenant graph disclosureSeed two tenants; assert every API and graph path returns only authorized records
Overpowered GitHub integrationAudit installed scopes; prove read-only mode cannot write or merge
Malicious remediation diffSchema / diff validation, human approval, isolated CI, proposal-hash binding
Graph query abuseReject unsupported templates; enforce depth, timeout, row count and tenant filters
SSRF through external URLsBlock loopback, link-local, private ranges, bad redirects and metadata endpoints
False “fixed” statusAttempt closure with failed / missing verification and assert rejection

14 · Test plan & evaluation

Ten acceptance tests that define “working”

Ingesting the same GitHub event twice creates no duplicate entities or findings
A known multi-hop test graph returns the expected path and ordered relationships
Removing an access relationship eliminates the path after recomputation
Every attack-path step links to evidence or is labeled unverified inference
Severity and risk factors reproduce from stored deterministic inputs
No remediation applies without approval and a matching proposal hash
A finding cannot reach verified_fixed when tests fail or are missing
Cross-tenant API, graph, job and artifact access is denied
CI reports stale or failed ingestion instead of an unqualified pass
The app sets up from the README in a clean environment

17 · Assumptions, decisions & exclusions

What we assume, decide and won't build

Assumptions
  • Audience: businesses using AI coding agents and MCP internally
  • First integration: GitHub repos and CI/CD
  • Track: Agents That Act on Connected Data
  • FalkorDB is essential to attack-path reasoning
  • Demo uses synthetic or public data
  • Core submission work is new event work
Decisions to confirm
  • GitHub App permissions: read-only or also open PRs
  • FalkorDB deployment mode, version, client, syntax
  • Which scanner outputs the demo imports
  • Whether the LLM may receive source excerpts, and redaction
  • Mandatory verification checks before closure
Out of scope for MVP
  • Universal prompt-injection protection claims
  • Autonomous code changes or auto-merged PRs
  • Arbitrary LLM-generated Cypher
  • Exploitability claims from connectivity alone
  • Every agent framework, MCP server and CI provider
  • Production secrets or customer data in the demo
